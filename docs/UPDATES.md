## الطلبات

- يحتفظ التطبيق بالسلة ومحاولة التأكيد على الجهاز، مفصولة حسب السيرفر ورقم حساب الطالب.
- قبل إرسال الطلب يُحفظ `request_key`. إعادة المحاولة بنفس المحتوى تستخدم المفتاح نفسه، حتى بعد إعادة تشغيل التطبيق.
- يحتفظ السيرفر بنتيجة المحاولة داخل المعاملة نفسها. تكرار المفتاح يعيد الطلب الموجود دون حجز جديد أو إشعار إضافي.
- المفتاح خاص بالطالب. استخدامه مع محتوى مختلف يرجع `409`. العملاء القدماء دون مفتاح ما زالوا مدعومين، لكن لا يحصلون على حماية إعادة الإرسال.
- التحقق من سعة الاستلام وإنشاء الطلب يتمان بعد قفل صف الكافيتريا في قاعدة البيانات. القفل يعمل بين عمليات السيرفر، مع SQLite وPostgreSQL، وليس داخل عملية واحدة فقط.
- الانتقال إلى الحالة التالية فقط: `received → preparing → ready → delivered`. مسح QR قبل `ready` مرفوض.
- يستطيع الطالب الإلغاء، وتستطيع الكافيتريا الرفض مع السبب، أثناء `received` فقط. الحالات الجديدة `cancelled` و`rejected` تظهر في السجل وتحرر سعة الاستلام، ولا يمكن تقييمها أو تسليمها.
- يسجل جدول `order_events` الإنشاء وكل تغيير للحالة مع الجهة والوقت والسبب.

- تغيير كلمة مرور الطالب أو رمز الكافيتريا من الواجهة ينهي الجلسات القديمة باستخدام `auth_version`.
- حد الدخول: عشر محاولات لكل حساب خلال خمس دقائق، محفوظ في قاعدة البيانات ليعمل عبر عمليات السيرفر. اضبط حدودًا إضافية على مستوى البنية التحتية قبل فتح خدمة عامة كبيرة.
- في `WAJBATI_ENV=production` أو Render لا يُنشأ الحساب التجريبي. أول تهيئة إنتاجية تحتاج رموز كافيتريات خاصة داخل `WAJBATI_CAFETERIA_CODES` ومفتاح `WAJBATI_SECRET`.
- البيانات التجريبية الموجودة مسبقًا لا تُحذف تلقائيًا. قبل استخدام قاعدة تطوير للإنتاج، غيّر رموزها وكلمة مرور الحساب التجريبي أو استخدم قاعدة إنتاج جديدة.

## تفعيل إشعارات الهاتف لاحقًا

لا يوجد مشروع Firebase مهيأ حاليًا. الربط موجود ولكنه معطل افتراضيًا، ويستمر التطبيق بالعمل عبر الإشعارات الداخلية.

1. أنشئ مشروع Firebase وسجّل تطبيق Android بالـapplicationId النهائي. المعرّف الحالي `com.example.wajbati_dashboard` تجريبي. لتطبيق iOS سجّل الـbundle ID النهائي؛ الحالي `com.example.wajbatiDashboard`.
2. انسخ قالب `config/firebase.android.example.json` إلى `config/firebase.android.local.json` واملأ قيم إعداد تطبيق Firebase. استخدم قالب iOS مستقلًا لأن `FIREBASE_APP_ID` يختلف بين المنصتين.
   نزّل ملف Android `google-services.json` إلى `android/app/` لتهيئة Firebase الأصلية عند تشغيل التطبيق في الخلفية. يتم تفعيل Google Services Gradle plugin تلقائيًا عند وجود الملف. يجب أن تتطابق هذه الإعدادات مع ملف إعدادات Dart. في iOS أضف `GoogleService-Info.plist` إلى Runner عبر Xcode مع تفعيل Target Membership.
3. شغّل `flutter run --dart-define-from-file=config/firebase.android.local.json --dart-define=API_URL=https://YOUR-API`.
4. في السيرفر اضبط `FCM_SERVICE_ACCOUNT_JSON` أو `FCM_SERVICE_ACCOUNT_FILE` بحساب خدمة المشروع نفسه. لا تضع مفتاح حساب الخدمة داخل التطبيق أو المستودع.
5. في iOS فعّل Push Notifications وBackground Modes / Remote notifications داخل Xcode، واضبط APNs credentials في Firebase والتوقيع المناسب. لا توجد شهادات أو provisioning profiles مضافة للمشروع حاليًا.
6. اسمح بالإشعارات عند طلبها، سجّل دخول طالب، أرسل طلبًا، أغلق التطبيق، ثم غيّر حالته من جهاز الكافيتريا. جرّب الضغط على الإشعار لفتح الطلب، ثم الخروج من الحساب للتأكد من توقف إشعاراته.

الربط يستخدم FirebaseOptions صريحة من إعدادات البناء، ويسجل الجهاز وتجديد رمزه ويفتح الطلب من الإشعار. توجد قناة Android باسم `orders`. فشل الإعداد أو التسجيل لا يمنع تسجيل الدخول أو الطلب، ويُعاد التسجيل عند التحديث اللاحق.

المرجع: [إعداد FCM لتطبيق Flutter](https://firebase.google.com/docs/cloud-messaging/flutter/get-started)، [استقبال الرسائل](https://firebase.google.com/docs/cloud-messaging/flutter/receive-messages)، [إعداد Firebase الأصلي في Android](https://firebase.google.com/docs/android/setup).

